<objective>
Wire the resolution rule from plan 05-02 into the three account-creation paths through a single
shared internal seam, and ship the idempotent backfill that links the six live `agentbox3`
accounts using that same rule.

D-01/D-02 settled where the hook goes and the codebase confirmed it: the OAuth callback creates
zero accounts, and there is no existing choke point — `createAccount` (:310),
`createImapAccount` (:128) and `createMicrosoftAccount` (:186) each own an independent write.
This plan introduces the choke point, then calls it once per creator after the branch resolves.

Purpose: ENT-01 and ENT-05 (silent auto-create on any provider connect), ENT-03 via D-16
(sibling-domain attach), and MAP-04 / D-09 / D-10 / D-11 (a re-runnable backfill that exercises
the runtime rule rather than duplicating it).

Output: the seam in `queries-accounts.ts`, its real-Postgres test coverage including the
sentinel-adopt branch, and `scripts/business-link-backfill.ts` behind `npm run business:backfill`.
</objective>

**The seam.** Add a module-internal (not exported) `persistAccountLink` to
`dashboard/lib/queries-accounts.ts` that takes the resolved account id, email, and display
label, and delegates to `linkAccountToBusiness` from `@/lib/crm/auto-link` inside a try/catch

Await the call rather than firing it with `void`. PATTERNS conflict #3 flags both options and
resolves in favour of await: `inbox-messages` uses `void` because it sits on a five-minute
polling hot path where latency per ingest matters, while account connect happens a handful of
times ever per appliance. Awaiting means `business_id` is populated in the same request that
created the account, so the Accounts settings page shows the linked business immediately rather
than after a refresh — which is what D-06's "silent" auto-create should feel like.

**The three call sites.** In `createImapAccount` and `createMicrosoftAccount`, restructure so

if/else, immediately before the single `return result`. This is the entire point of D-02 and the
structural defence against Pitfall 1: with one call site per function positioned after the
branch resolves, it is impossible to wire the insert path and forget the adopt path. Pass the
input email and display label — the same values that were just written to the row — not a
re-read of the row.

`createAccount` has no adopt branch. Call the seam once after its `INSERT ... RETURNING`
