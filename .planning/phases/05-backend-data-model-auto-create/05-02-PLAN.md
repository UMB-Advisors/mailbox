`generateUniqueSlug(name)` — start from `generateSlug(name)`, then probe
`SELECT 1 FROM mailbox.businesses WHERE slug = $1` and append an incrementing numeric suffix
until the candidate is free. Cap the probe loop at 100 attempts and throw past that; the caller
boundary is non-fatal so an escaped throw degrades to "unlinked account", never a hung request.
This loop is safe at this table's row count (single digits today) and mirrors the app-side-UX /
DB-constraint-guarantee split: the unique index created in plan 05-01 is the real guarantee,
this loop just avoids surfacing a raw 23505 to the caller.

`findBusinessIdBySiblingDomain(domain)` — this is D-16's exact lookup and the literal
implementation of ENT-03. Query
`SELECT business_id FROM mailbox.accounts WHERE split_part(email_address, '@', 2) = $1 AND business_id IS NOT NULL ORDER BY id LIMIT 1`
and return the id or null. Parse the domain inside SQL with `split_part` rather than fetching
rows and filtering in JS — that is this repo's established convention (see `BARE_ADDR_SQL`).
No self-exclusion clause is needed: the calling account's `business_id` is null at this point by
construction, and the backfill only ever processes null rows, so the `IS NOT NULL` predicate
already excludes it.

`findOrCreateBusiness(name)` — D-08's locked shape.
`INSERT INTO mailbox.businesses (name, slug) VALUES ($1, $2) ON CONFLICT (name) DO NOTHING RETURNING id`,
then when zero rows come back, `SELECT id FROM mailbox.businesses WHERE name = $1`. Zero rows
from the fallback is unreachable (a conflict implies the row exists) but throw a descriptive
error there anyway rather than returning a bogus id — the caller boundary swallows it. Compute
the slug with `generateUniqueSlug(name)` before the INSERT. Do not reach for the
`DO UPDATE ... RETURNING xmax = 0` variant: D-08 locks `DO NOTHING` + fallback SELECT, and the
`{ id, created }` result shape matches the house convention already used by
`POST /api/internal/inbox-messages` (PATTERNS conflict #2 resolves this in favour of `created`
for anything CRM-side; `adopted` stays specific to the sentinel-account concept).

`linkAccountToBusiness({ accountId, email, displayLabel })` — the single entry point, wrapping
its entire body in one try/catch that logs and returns rather than rethrowing (D-05). Use the
`console.error('[auto-link] ... (non-fatal)', err)` log-and-swallow shape from
`app/api/internal/inbox-messages/route.ts`'s `embedAndUpsertInbound`. Resolution order is fixed
by D-16 and must be implemented exactly:

1. Skip entirely and return when `email` is the appliance sentinel address
   `primary@appliance.local` — an unclaimed sentinel row is not a real mailbox and must never
   produce a business named after the appliance host. (The runtime hook cannot receive it, since
   the adopt branch rewrites the address before linking, but the backfill script in plan 05-03

2. `domain = extractEmailDomain(email)`.
3. When the domain is NOT free-mail, run `findBusinessIdBySiblingDomain(domain)`. A hit ends
   resolution — attach to that business and skip find-or-create entirely.
4. Otherwise (free-mail domain, or a non-free-mail domain with no linked sibling), resolve the
   name via `resolveBusinessName(email, displayLabel)` and call `findOrCreateBusiness(name)`.
5. Persist: `getKysely().updateTable('accounts').set({ business_id: businessId }).where('id', '=', accountId).execute()`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator input → SQL | `display_label` (operator-supplied via the Accounts settings UI, zod-validated at the route boundary per STAQPRO-138) becomes a business `name` and a `slug`, both of which reach new SQL in this module. This is the only untrusted-ish value crossing into new dynamic SQL this phase. |
| account connect flow → auto-link | The linker runs inside the account-creation call stack. A failure here must degrade to "unlinked account", never to "connect failed". |

Note: this plan adds no HTTP route and no new authorization boundary. The appliance is
